01 BASICS

What is a Java Servlet?

The fundamental building block of server-side Java web development.

☕

WHAT IS IT?

A Java Servlet is a Java class that lives on a web server. When you click a link or submit a form in your browser, the Servlet wakes up, reads your request, computes data, and sends back a response (HTML page, JSON data, or file).

A Servlet is a Java technology managed by a ServletContainer implementing the Jakarta/Java EE Servlet specification (e.g., jakarta.servlet.http.HttpServlet). It provides component-based, platform-independent server extension capabilities without vendor lock-in.

💡 REAL-WORLD ANALOGY: Think of a Servlet like a receptionist at an office desk. Visitors (browser requests) arrive, the receptionist reads their form, grabs what they need from the back office, and hands them an answer ticket.
⚡

WHY DO WE USE IT?

Before Servlets, servers used CGI (Common Gateway Interface). Every single visitor started a heavy new operating system process, freezing servers when hundreds visited! Servlets fixed this by using lightweight threads inside one single Java process.

CGI spawned an OS-level process per request incurring significant fork/exec overhead. In contrast, Servlets execute within a persistent JVM process using a pooled multithreaded architecture (thread-per-request model), achieving orders-of-magnitude lower memory consumption and response latency.

❌ CGI: 1000 visitors = 1000 OS processes (Server crashes) ✓ Servlet: 1000 visitors = 1000 lightweight threads in 1 JVM
⚙️

WHAT IS A SERVLET CONTAINER?

A Servlet cannot run by itself like a normal Java main() program. It needs a Servlet Container (such as Apache Tomcat or Jetty) to manage its entire life, listen on network ports, handle security, and route requests to it.

The Servlet Container (Web Container) is the runtime environment implementing the Servlet API contract. It handles TCP/IP socket listening, HTTP request header parsing, thread pooling, session persistence, security constraints, and delegates to the appropriate Servlet instance via mapping descriptors.

🏢 REAL-WORLD EXAMPLE: Apache Tomcat is the most famous open-source Servlet Container in the world. It provides the house where your Servlets live.

03 LIFECYCLE

The Servlet Lifecycle Rings

A Servlet is born, serves thousands of visitors, and gracefully retires. See the 6 stages in action.

6 Lifecycle Portal Stages: Loading, Instantiation, init(), service(), doGet()/doPost(), destroy()
1

1. Class Loading

ONCE ONLY

Tomcat searches for HelloServlet.class and loads the bytecode into JVM memory.

✓
2

2. Instantiation

ONCE ONLY

Tomcat calls the default constructor new HelloServlet() to create the single instance in memory.

✓
3

3. init()

ONCE ONLY

Tomcat passes ServletConfig. Initializes database pools, config files, or external services.

✓
4

4. service()

EVERY REQUEST

Tomcat allocates a lightweight thread and calls service(request, response) for every single visitor!

✓
5

5. doGet() / doPost()

EVERY REQUEST

The specific HTTP worker method you wrote executes, reads input, and writes the output stream.

✓
6

6. destroy()

ONCE ON SHUTDOWN

Tomcat calls destroy() right before shutting down or reloading to close open database sockets and clean up memory.

✓

CLICK A METHOD IN THE CODE TO HIGHLIGHT ITS LIFECYCLE STAGE:

@WebServlet("/hello")
public class HelloServlet extends HttpServlet {

    
    public void init(ServletConfig config) throws ServletException {
        // Runs ONCE when Servlet is born. Setup DB pools here.
    }
    

    
    protected void service(HttpServletRequest req, HttpServletResponse res) {
        // Runs for EVERY visitor. Inspects HTTP method and routes!
        super.service(req, res);
    }
    

    
    protected void doGet(HttpServletRequest request, HttpServletResponse response) {
        // Runs for EVERY GET request. Your custom logic lives here!
    }
    

    
    public void destroy() {
        // Runs ONCE before server stops. Close connections & clean memory!
    }
    
}

07 ARCHITECTURE

JSP vs Servlet: Where Does Each Belong?

Why do we have both, and how do they collaborate in modern MVC web architectures?

☕

SERVLET

The Controller (Brain)
  • What is it? Pure Java code that generates HTML.
  • Best for: Business logic, handling inputs, authentication, database routing.
  • Drawback: Writing HTML inside out.println("<div><h1>...") is messy and error-prone!
📄

JSP (JavaServer Pages)

The View (Presentation)
  • What is it? HTML template containing embedded Java tags or EL ${user.name}.
  • Best for: Designing beautiful web pages, tables, styling, and visual layout.
  • Drawback: Writing complex calculations and database calls inside HTML creates spaghetti code!
THE WINNING COMBINATION: MODEL-VIEW-CONTROLLER (MVC)
1 Browser Request Visits /dashboard
➔
2 Servlet (Controller) Computes math, queries DB
➔
3 RequestDispatcher forward(request, response)
➔
4 JSP (View) Renders HTML with ${data}
➔

Anatomy of a Real Java Servlet

Click on any keyword, annotation, or parameter in the code below to see its exact role.

📄 HelloServlet.java
Click any glowing keyword! 
@WebServlet("/hello")
public class HelloServlet extends HttpServlet {

    @Override
    protected void doGet(
        HttpServletRequest request,
        HttpServletResponse response)
        throws ServletException, IOException {

        // 1. Set response content type to HTML
        response.setContentType("text/html");

        // 2. Read query parameter from URL (?name=...)
        String userName = request.getParameter("name");

        // 3. Get output writer to stream HTML to browser
        PrintWriter out = response.getWriter();

        // 4. Print response body
        out.println("<h1>Hello, " + userName + "!</h1>");
    }
}
